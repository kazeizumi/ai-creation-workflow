# Intake and gates

## Establish the task before routing

Reuse confirmed conversation and project facts first. Fill only fields whose
absence can change the direction, scope, cost, permission, route or acceptance:

- final goal and intended use;
- concrete deliverables and current project stage;
- authoritative inputs and decisions already locked;
- format, quality, time, cost, tool and platform constraints;
- evidence that will prove completion;
- actions the assistant may perform and items outside scope.

Resolve several related unknowns in one compact question. Use a reversible
default for ordinary implementation details. Showing a plan is information; it
does not create an approval gate.

## Use gates only for consequential decisions

A gate is justified when the user must choose or authorize one of these:

- the requested result itself needs user review before downstream work;
- two plausible directions would produce materially different results;
- a creative lock freezes script, composition, voice or another costly input;
- an action spends money, publishes externally, changes external state or is
  difficult to reverse;
- a sample must be accepted before a larger batch.

Do not stop for project reads, drafts, skill handoffs, dry runs, local
validation, state updates, evidence capture or recovery of the same known job.
Reuse an existing authorization while its purpose, input, scope, output and
failure fallback remain unchanged.

Each gate records the exact decision, why it matters, evidence presented,
authorization scope and resulting state. After it passes, continue through all
covered steps without asking again.
