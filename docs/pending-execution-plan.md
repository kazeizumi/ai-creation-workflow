# 待执行计划：双核心工作流与可插拔领域包

状态：`in_progress`
更新日期：2026-09-10

这份计划固定项目后续的设计方向。Phase 0 的 Token 与子代理调度规则已经落实，其余代码任务仍按本计划等待执行。

## 一、最终定位

系统由两个核心组成：

| 核心 | 对谁负责 | 主要职责 |
|---|---|---|
| 技能管家 `skill-governor` | 对内部能力库负责 | 发现、登记、分配、查重、试用、评分、更新、隔离、可恢复退役 |
| 工作流总控 `ai-creation-workflow` | 对用户目标和最终交付负责 | 摸清需求、确定范围、拆解步骤、管理依赖、调用专业能力、推进执行、验收和交付 |

用户日常只面对工作流总控。总控决定当前需要什么能力，技能管家从现有技能库中返回最合适的主 Skill 和必要专项；专业 Skill 负责具体工艺，总控收回产物后继续推进。

AI 视频制作是工作流总控下的第一个领域包，不是第三个核心。H3、本地 ComfyUI、云端 AutoDL、剧本、分镜、提示词、VFX 和声音都是这个领域包中的阶段或专业能力。以后可以增加代码开发、长文写作、研究、图片、音乐等领域包，而不用改写两个核心。

```text
用户
└─ 工作流总控
   ├─ 需求摸清与项目计划
   ├─ 技能管家
   │  └─ Skill 发现、分配、学习、评分与退役
   └─ 可插拔领域包
      ├─ AI 视频制作
      │  ├─ 剧本 / 导演 / 分镜 / 提示词 / VFX / 声音
      │  └─ H3 → 本地 ComfyUI 或云端 AutoDL
      ├─ 代码开发（未来）
      ├─ 长文写作（未来）
      └─ 其他工作流（未来）
```

## 二、最重要的前置阶段：摸清用户需求

方向错误会让所有下游产物一起返工，因此总控必须先判断需求是否足以开始。它先复用对话、项目文件和已确认选择，再补真正缺失的信息，不要求用户填写固定长表格。

### 必须建立的需求契约

| 信息 | 需要得到什么 |
|---|---|
| 最终目标 | 用户最后要得到什么，而不只是当前动作 |
| 交付物 | 文件、格式、数量、版本、语言和保存位置 |
| 使用场景 | 发布平台、受众、内部试验或商业交付 |
| 当前阶段 | 从零开始、已有草稿、已有锁定内容或只差执行 |
| 权威输入 | 哪些文件和版本是当前依据 |
| 核心约束 | 内容、风格、时长、规格、工具、预算和期限 |
| 质量标准 | 什么证据能证明完成，哪些判断必须由用户作出 |
| 操作范围 | 可以自动做什么，哪些外部动作需要授权 |
| 排除范围 | 这次明确不做什么，避免任务无边界增长 |

### 提问规则

1. 能从当前会话和项目材料查到的先查，不重复询问。
2. 可撤销、低影响细节采用合理默认，并在计划中标明。
3. 只有缺失信息会改变方向、范围、成本、权限、执行路线或不可逆结果时才问。
4. 通常一次只问最关键的问题；强相关问题可以合并成一组，避免多轮零碎打扰。
5. 用户回答后更新需求契约，只让真实依赖旧答案的下游失效。
6. 未锁定的创意判断不能被系统写成“用户已通过”。

### 需求阶段验收

- 模糊目标能定位出当前最关键缺口；
- 已经完整的请求不会被再次盘问；
- 总控能复述最终交付、当前输入、关键约束和完成标准；
- 计划中的每个步骤都能追溯到一项交付或风险；
- 方向仍不明确时不进入高成本生产。

## 三、任务规模与计划深度

| 模式 | 判断 | 实际行为 |
|---|---|---|
| `direct` | 单个明确、输入齐全、返工局部 | 直接调用已知 Skill 或工具并交付，不建正式计划 |
| `light` | 少量有依赖的步骤，方向已经锁定 | 简述步骤后执行，只记录必要检查点 |
| `full` | 上游决定下游、多阶段交接、批量、跨会话或需要恢复 | 建立需求契约、阶段计划和状态文件，持续推进到交付 |

Full 模式必须让用户看见目标、步骤、主要分工和真实门禁，但“展示计划”不等于“强制暂停”。范围已经授权且没有未决方向时，总控展示后继续执行；用户要求先审、存在关键选择、新增费用、新权限或不可逆操作时才暂停。

## 四、执行阶段的低打扰门禁

### 必须暂停的情况

1. 用户明确要求先看方案、先审核或先不要执行；
2. 缺少会改变主题、交付范围、核心效果或执行路线的选择；
3. 新建或改变需要用户锁定的剧本、品牌方向或关键创意；
4. 真实启动付费实例、提交 ComfyUI、批量渲染或其他会持续产生费用的动作；
5. 外部发布、发送、覆盖、删除、不可恢复替换等外部或不可逆操作；
6. 代表性样片尚未放行，却准备扩大到批量生产；
7. Skill 合并、停用或退役将改变现有项目依赖。

### 不应暂停的情况

- 读取项目和恢复状态；
- Skill 的内部选择与交接；
- 创建草稿、计划、清单和本地可撤销文件；
- dry-run、静态检查、格式验证和只读诊断；
- 已授权范围内的连续步骤；
- 对实际产物进行技术验收；
- 保存任务 ID、更新状态和记录可归因证据；
- 超时后查询同一个外部任务。

### 门禁呈现方式

需要暂停时一次给全当前决策所需信息：准确动作、输入、数量、输出、费用或影响、失败处理和恢复方式。用户确认后，同一范围内的内部步骤不再重复询问。范围、输入或费用发生实质变化时才建立新门禁。

## 五、领域包兼容与扩展接口

领域包负责提供某类工作的阶段模板和专业规则，不接管项目总控。每个领域包需要声明：

| 字段 | 含义 |
|---|---|
| `pack_id` | 稳定领域标识，例如 `ai-video` |
| `triggers` | 什么时候进入该领域 |
| `stage_templates` | 可选阶段及依赖，不要求每个项目全部执行 |
| `artifact_contracts` | 各阶段输入、产物和验收证据 |
| `specialist_lanes` | 需要技能管家分配的专业能力域 |
| `required_gates` | 本领域真正必须暂停的动作 |
| `runtime_adapters` | 可选执行后端及其能力条件 |
| `failure_policy` | 超时、失败、恢复和降级规则 |

兼容原则：

1. 保留现有 Skill 名称和调用方式，升级不破坏已有项目。
2. 两个核心只依赖领域包契约，不硬编码 H3 或视频阶段。
3. 领域包可以只提供部分阶段；总控按当前交付走最短有效路径。
4. 新领域包通过登记接入，不要求修改核心流程代码。
5. 能力相近的 Skill 先比较来源、行为指纹和边界；不能仅凭名称设成别名。
6. 明确候选复用已有映射；候选竞争、缺口或失败时才启动更深的技能检索。

## 六、AI 视频领域包的实际分支

```text
需求与已有材料
→ 剧本锁定（已有锁定稿时跳过）
→ 内容单元 C
→ 故事镜头 SH
→ 实际生成段 G
→ 当前批次资产与必要故事板
→ 中英文提示词和真实上传顺序
→ H3 运行选择
   ├─ 本地 ComfyUI
   └─ 云端 AutoDL
→ 实际视频验收
→ 剪辑 / VFX / 声音 / 调色
→ 用户最终验收与交付
```

简单单镜头可以直接从已有材料进入提示词或执行阶段。批量任务先做代表性或高风险样片，确认后再扩展。每次真实 ComfyUI 提交都要有当前运行契约；轮询超时先恢复原 `prompt_id` 或任务 ID，不盲目重提。

## 七、技能管家的学习与退役闭环

### 正常分配

总控发送：当前产物、输入版本、目标工具、约束、验收和缺口。技能管家返回：一个主 Skill、必要专项、边界、排除理由和缺失输入。

### 学习

- `record-use` 记录选用、完成、部分完成、失败或替代；
- `record-outcome` 只记录能够归因的真实反馈或测试；
- 使用频率和质量评分分开；
- Skill 更新后旧证据保留，新版本重新试用；
- 项目整体评价不复制给所有参与 Skill。

### 待补齐的退役执行能力

需要新增可恢复操作，而不只写规则：

1. `prepare-retire`：检查替代者、独特能力、A/B、近期使用和项目依赖；
2. 生成退役计划：目标、影响、归档位置、恢复命令和证据；
3. 用户明确批准后执行 `retire`；
4. 把 Skill 移入日期化归档并写入 `skill-retirements.json`；
5. 提供 `restore-retired`，验证备份后恢复；
6. 系统和插件管理的 Skill 保持受保护状态。

## 八、实施阶段

### Phase 0：Token 与子代理调度（已落实规则）

- 默认使用自适应 Token 策略：direct/light 从精简上下文开始，full 只加载需求契约、决策索引、当前阶段和直接依赖；
- 稳定事实只保存一次，下游使用路径、版本和决策 ID；
- 已确认且输入、工具、约束、映射均未变化的 Skill 分配直接复用；
- 执行当前阶段时才读取对应 Skill 和必要参考，不提前加载后续能力；
- 只有两个以上独立 `ready` 节点、写入互斥、契约完整、并行收益大于协调成本且运行规则允许时，才创建子代理；
- 子代理只接收精简节点包，根代理负责用户沟通、整合和最终验收。

验收：减少重复读取、全库扫描、长交接和无收益委派；需求、授权、专业方法与必要验证保持完整。

### Phase 1：核心行为与需求入口

- 新增统一需求契约和精简计划卡；
- 把需求复用、关键缺口判断和提问规则写入总控；
- 增加“计划展示”和“用户审批”两个独立状态；
- 建立需求完整、需求模糊、已有授权、用户要求先审等交互测试。

验收：方向不清时能问到关键点；方向清楚时不重复询问；Full 项目能展示计划后在授权范围内继续。

### Phase 2：门禁瘦身与状态恢复

- 将门禁限定为本计划第四节列出的高影响节点；
- 已有授权写入项目状态并按范围复用；
- 新范围、输入版本或费用变化时使对应授权失效；
- 外部超时优先查询原任务；
- 统一待用户评价、必须暂停和技术失败三类状态。

验收：内部步骤不连续弹确认；一次付费生成只出现一次完整授权；续作不要求用户重述已确认信息。

### Phase 3：领域包接口

- 定义领域包清单和字段校验；
- 把 AI 视频阶段从核心说明迁入 `ai-video` 领域包；
- 核心通过领域包接口获取阶段、产物、门禁和失败策略；
- 增加一个最小非视频示例，证明扩展时无需修改核心。

验收：非视频任务不加载 H3 规则；新增示例领域包不改两个核心；旧 AI 视频调用继续可用。

### Phase 4：技能生命周期执行器

- 增加技能库初始化和本机扫描流程，不提交机器相关注册表；
- 补充试用、同题 A/B、评分和审计测试；
- 实现可恢复退役与恢复；
- 只对来源和行为完全等价的 Skill 建立别名，其余进入重叠对比。

验收：新 Skill 默认试用；质量证据绑定当前指纹；退役前生成影响报告；归档后能够恢复。

### Phase 5：运行时可靠性

- 修复云端 `--dry-run` 写状态和覆盖恢复信息的问题；
- 为本地长轮询增加低频心跳；
- 使用明确的 `AUTODL_ENV_FILE` 或用户配置文件定位 Token，不向上盲搜 `.env`；
- 加固 Windows Python/httpx 检测；
- 优化面板探测并保留同一任务 ID 的恢复路径。

验收：dry-run 不修改已有状态；Token 不进入仓库；长任务有进度；超时不会造成重复付费提交。

### Phase 6：开源验证与发布

- 调整生成缓存检查，避免正常测试后出现假失败，同时阻止缓存进入发布包；
- 泛化私有绝对路径和凭据扫描；
- 增加 Windows 与 Linux CI；
- CI 执行结构验证、技能管家测试和本地/云端 dry-run；
- 清理文档中的临时绝对路径。

验收：干净克隆可完成初始化；CI 全部通过；发布文件不含 Token、私有路径、机器注册表和生成缓存。

## 九、端到端验收场景

1. 用户只说“帮我做一个宣传片”：总控先定位受众、交付和关键方向，不立即生成。
2. 用户给出完整单步骤需求：直接执行，不强制建立 Full 计划。
3. 用户启动多阶段项目：展示精简计划，已授权部分继续推进。
4. 用户说“生成 H3 视频”但未选运行位置：只询问云端还是本地。
5. 用户给出完整 H3 契约并授权：只出现一次执行门禁。
6. 云端轮询超时：查询原任务 ID，不创建第二个付费任务。
7. 新增一个 Skill：进入试用，通过真实证据后才进入主路由。
8. 两个 Skill 功能相近：进入同题 A/B，不按名称直接合并。
9. 退役一个 Skill：先展示依赖、替代者、备份和恢复方式，批准后归档。
10. 添加非视频领域包：总控能够执行，AI 视频规则不会污染该项目。
11. 跨会话回复“继续”：读取原项目状态，从第一个可执行或可恢复节点开始。
12. 修改上游内容：只让真实依赖旧版本的下游失效。
13. 两个独立节点同时 ready 且写入互斥：允许创建子代理并行交付。
14. 多个步骤修改同一文件或依赖前序输出：保持根代理串行执行。

## 十、明确不做

- 不把 AI 视频写死为整个系统的唯一流程；
- 不让技能管家取代项目总控；
- 不让工作流总控直接修改或淘汰 Skill；
- 不要求所有 Full 任务先强制停机等待确认；
- 不为内部读取、交接、检查和状态更新增加门禁；
- 不自动安装未知 Skill；
- 不把使用次数当成质量；
- 不自动永久删除 Skill；
- 不把提示词、故事板或命令成功当成实际成片验收。
