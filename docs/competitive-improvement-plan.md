# 双核心 Skill 竞品对标与二轮迭代计划

状态：`P0 + P1 已完成；发布状态以 GitHub 提交与 CI 为准`

更新日期：2026-09-10

## 1. 目标与边界

本轮不是把项目改造成通用 Agent 框架，而是验证并加强两个核心：

- `ai-creation-workflow`：负责摸清需求、生成计划、管理依赖与状态、调度执行、减少无效门禁、验收和交付。
- `skill-governor`：负责 Skill 的发现、分配、重叠对比、学习、评分、更新和可恢复退役。
- 把“当前 Skill 能否胜任”作为每个新能力节点的必要判断；存在真实缺口时，按“复用当前能力 → 本地发现 → 在线搜索 → 安全试用 → 自建或局部优化”闭环补齐。
- AI 视频继续是一个可插拔领域包，不升格为第三个核心。
- 不直接搬运竞品代码，不引入大型框架依赖；只吸收能用当前 Skill + 脚本架构验收的机制。
- 本计划通过后才修改代码和文档，通过全部验收后才推送 GitHub。

## 2. 对标对象

| 项目 | 对标重点 | 值得吸收 | 不直接照搬 |
|---|---|---|---|
| [open-source-video-gen-skill](https://github.com/mini-yifan/open-source-video-gen-skill) | AI 视频、H3、AutoDL、场景化 Skill 组合 | 单镜头快速路径、高风险样片先行、自动开关机、用户面向的场景入口 | 视频专用模板不能取代可扩展总控；不把每个阶段都变成必停门禁 |
| [LangGraph](https://github.com/langchain-ai/langgraph) | 持久化状态、故障恢复、人在回路、可观测性 | 显式状态转换、检查点、幂等恢复、门禁前后的决策记录 | 不把便携 Skill 包改成需要数据库和服务端的工程框架 |
| [CrewAI](https://github.com/crewAIInc/crewAI) | 角色式多 Agent 与事件驱动 Flow | 根 Agent/专项 Agent 职责分离、明确交接契约、可观测的委派决策 | 不按 Skill 数量创建 Agent，不为了“多 Agent”增加 Token 和协调成本 |
| [Anthropic Skills](https://github.com/anthropics/skills) | Skill 的自包含结构、渐进加载和可移植性 | 每个 Skill 的指令、脚本、引用和资产可独立安装；必要的前向测试 | 示例技能库本身不等于 Skill 学习、评分和退役系统 |

这四类对象分别覆盖“视频专项体验”、“持久工作流”、“多 Agent 编排”和“Skill 包规范”，避免只跟一个仓库比功能数量。

## 3. 统一对比维度

每个竞品和当前项目都用同一张证据表评估：

1. 需求入口：能否复用已有上下文，只追问会改变方向的缺口。
2. 路由与边界：总控、管家、专业 Skill 和执行器是否互不越界。
3. 扩展性：新增非视频领域是否需改核心逻辑。
4. 状态与恢复：断点续作、上游变更、外部任务超时是否会重复执行。
5. 门禁体验：只在创意锁定、费用、外部发布或不可逆操作前暂停。
6. Skill 治理：发现、映射、重复、来源、版本指纹和安全更新。
7. 学习与退役：使用证据与质量评分是否分开，退役是否有替代者、A/B、依赖审查和恢复路径。
8. Token 和委派：是否避免重复读取，子代理是否只接收有界输入包。
9. 安装与可移植：单个 Skill 安装后所需模板、脚本和引用是否齐全。
10. 可验收性：是否有 Windows/Linux CI、离线 dry-run、故障恢复和凭据泄漏检查。

结论不采用单一总分。每个维度输出：当前证据、竞品优点、本项目优点、真实缺口、拟采用机制、不采用原因和验收方法。

## 4. Skill 能力适配、搜索与自建闭环

这一闭环由 `skill-governor` 负责能力决策，由 `ai-creation-workflow` 负责把决策落到当前项目节点并继续执行。总控不亲自搜完全部 Skill，管家也不重新询问项目需求。

```text
总控提交当前节点契约
→ 管家生成能力签名
→ 复用未失效的历史路由
   ├─ 完全胜任：返回一个主 Skill 和必要专项
   ├─ 部分胜任：明确缺口，先查本地候选
   └─ 不能胜任：进入能力补齐
→ 本地精准搜索
→ 本地仍无合格候选时在线搜索
→ 候选清洗、安全/许可证/兼容审查、小样本前向测试
   ├─ 有合格候选：查重并推荐“完整安装 / 参考补强 / 不采用”
   │  └─ 用户未指定采纳方式时，只询问一次完整安装还是参考补强
   └─ 仍无合格候选：生成能力缺口规格，自建新 Skill 或局部改进现有 Skill
→ staging 验证与真实任务试用
→ 用户批准激活或更新共享 Skill 库
→ 总控继续原节点
→ 记录当前版本的使用和可归因质量证据
```

### 4.1 任务能力签名

总控只传递当前节点必要信息，管家将其归一化为可缓存签名：

```yaml
deliverable: 要产出的成果
input_types: 权威输入类型与版本
target_tool: 必须使用的工具或运行时
constraints: 只保留会影响选型的约束
acceptance: 可观测验收
permissions: 当前操作范围
```

缓存键为“阶段 + 交付物 + 工具 + 输入版本 + 关键约束”。签名和 Skill 行为指纹都未变时直接复用已验收路由，不重新扫描和评分。

### 4.2 胜任判定

判定顺序固定为：

1. 输入与交付物是否在 Skill 边界内；
2. 目标工具、平台和当前权限是否兼容；
3. 路由映射是否 `current`，来源和引用是否完整；
4. 当前版本是否有该场景的可归因证据；
5. 缺失部分能否由一个职责独立的专项 Skill 补足；
6. 预计 Token、时间、运行与维护成本是否合理。

输出三种结果：

- `fit`：完全胜任，返回一个主 Skill、必要专项和边界。
- `partial`：主 Skill 可完成大部分，但存在一个可明确描述的缺口；先寻找最小补充能力。
- `gap`：没有候选能完成关键交付或验收；不用高分但不适用的 Skill 勉强执行。

不使用脱离当前任务的单一总分自动决策。评分用于同样适用的候选比较，不能让“历史高分但不适配”的 Skill 获胜。

### 4.3 本地与在线搜索

为节省 Token，严格按层级升级：

1. 先查本次会话已选候选和未失效缓存。
2. 再查当前功能域的路标短名单，不读全部 Skill 正文。
3. 短名单不足时，查本地索引和已安装插件元数据。
4. 只在本地少于 2 个合理候选、或候选都不能填补缺口时，才搜索在线目录和 GitHub。
5. 在线候选先取名称、描述、来源、许可证、更新时间和 README；仅对排名靠前且边界匹配的 1–3 项读取行为文件。
6. 一旦足以判定“合格 / 不合格”就停止搜索，不为了给用户展示更多数量而继续拉取。

在线内容默认为不可信输入。搜索不需额外门禁；安装或激活第三方 Skill 会改变共享能力库，必须在一次完整展示来源、许可证、权限、依赖、写入范围、回滚和推荐项后获得用户批准。

候选有两个等价入口：用户交代安装的名称、路径、压缩包或 URL；以及技能管家为补齐缺口自行在线找到的候选。用户给出的候选可跳过“发现搜索”，但不能跳过查重、能力增益、安全、许可证、依赖、权限和兼容审查。两种入口的首要目标都是补强现有能力，不以增加 Skill 数量为目标。

### 4.4 有候选时的补齐策略

所有第三方候选先与现有能力做触发条件、输入、输出、工具、行为指纹和维护边界查重，再输出一张采纳决策卡：候选及来源、重叠项、独有增益、两种方式的影响、推荐方式、许可证/依赖/权限、写入范围、测试和回滚。

- `full_install`（完整安装）：候选有明确独立的触发、输入输出或工具边界，提供可验证且现有 Skill 难以承载的独有能力，并适合独立维护。它先进 staging，完整读取 `SKILL.md` 及必要引用，检查脚本、来源、许可证、外部依赖和权限，再用与当前节点同型的小样本测试；激活后先进入 `probation`，不自动取代原主 Skill。
- `reference_strengthen`（参考补强）：候选与已有 Skill 高度重叠，价值主要来自少量非显然的方法、验收器或参考资料，且许可证允许改编。只提取会改变决策的部分并保留来源/许可归属；对现有 Skill 做备份、三方差异审查、指纹更新和回归测试，不新增重复 Skill 目录。
- `reject`（不采用）：没有可测的独有收益，或来源、安全、许可证、依赖成本、权限和维护负担不合格。记录拒绝原因，避免下次重复深审。

若用户已明确“完整安装”或“只参考补强”，直接执行对应已批准路径，不重复提问；若未明确，只打断一次并附推荐：**“这个候选建议〔完整安装/参考补强/不采用〕，您要完整安装，还是参考后补强现有功能？”** 如果候选是实质重复项，默认推荐不安装；若用户仍选择完整安装，则保留显式重叠映射和较低初始路由优先级。

候选只有独立专项价值时，可作为补充 Skill，只负责缺失部分，不与原主 Skill 同时改写同一产物。候选与已有 Skill 大幅重叠但两种方式优劣不明时，先做同题 A/B，比较适配、产物、稳定、效率、维护、独特性和安全，再给推荐，不自动合并或替换。

### 4.5 没有合格候选时的创建或改进

管家先生成“能力缺口规格”，至少包含：触发场景、输入、产物、工具、真实边界、权限、验收、失败停止条件、与旧 Skill 的关系和预计 Token 收益。

然后按最小变更选择：

1. 现有 Skill 范围正确，只缺一个方法或验收器：局部优化现有 Skill。
2. 缺口是可独立复用的专项能力：创建新的狭 Skill。
3. 缺口是通用工具一次性能完成的小任务：直接使用工具，不为了补齐目录而新建 Skill。

创建或大改都在 staging 中完成，不直接覆盖活动共享库。先做结构验证、脚本测试和现实请求前向测试，再展示新增文件、行为变化、冲突、风险、回滚和激活范围。用户批准激活后，它以 `probation` 进入限定场景，不立即获得全局高优先级。

### 4.6 Token 与用户体验预算

- 一次能力请求只生成一份 `routing-decision`，总控、搜索器和创建器引用它，不复制整段对话。
- 候选列表默认最多 5 项，进入深审的默认最多 3 项，找到明确合格项即停。
- 先用元数据、能力签名和行为指纹查重；只完整读取最终 1–3 个候选及与其重叠的现有主 Skill，不把候选和全库 Skill 一起深读。
- 在用户选择“完整安装 / 参考补强”前，不读取与选择无关的大型实现、示例和依赖；选择后只加载该路径的必要材料。
- 用户只在两类节点被打断：缺少会改变能力选型的必要信息；或即将安装、激活、覆盖、合并、停用等改变共享能力库的动作。
- direct/light 任务不为记账另开扫描或审计；full 项目从已有节点汇总使用证据。
- 搜索与静态审查默认由根 Agent 串行完成。只有候选评估能分成两个以上输入完整、写入互斥且预计净节省的节点时，才考虑子代理。

### 4.7 状态与产物

计划实施时新增四个可审计产物：

- `capability-request.json`：当前节点的能力签名和验收契约。
- `routing-decision.json`：`fit | partial | gap`、主 Skill、专项 Skill、排除理由、缓存键和指纹。
- `gap-resolution.json`：本地/在线搜索范围、候选证据、采用或拒绝原因、创建/优化规格、当前门禁和恢复点。
- `candidate-adoption.json`：`full_install | reference_strengthen | reject`、候选来源、重叠/独有能力、推荐、用户已选方式、来源与许可、写入范围、测试、回滚和恢复点。

状态依次为 `assessing`、`fit`、`local_search`、`online_search`、`candidate_review`、`staging`、`awaiting_activation`、`probation`、`accepted` 或 `failed`。每次恢复先读现有产物，不重跑已完成搜索。

## 5. 基线缺口与修复结果

实施前的 5 个未推送提交虽已通过 6 个 Skill 的结构检查、领域包、Skill 治理、退役恢复、云/本地 dry-run 和运行恢复测试，但审读发现三个不应直接推送的缺口。本轮修复结果如下：

1. **单 Skill 安装不完整（已修复）**：三个项目模板已收入 `ai-creation-workflow/assets/templates`；顶层保留同步副本，独立安装测试检查资产存在和逐字节一致。
2. **状态枚举不一致（已修复）**：`stale` 已进入唯一状态契约；状态脚本验证转移、相同指纹幂等，以及只失效真实依赖后代。
3. **退役门禁强制不足（已修复）**：`prepare-retire` 现在强制读取结构化证据；缺项、证据漂移或 Skill 指纹漂移都会阻止 `retire`。

这三项是本轮 P0，不依赖竞品分析的主观判断，均已有离线回归覆盖。

## 6. 执行阶段

### Phase A：建立可追溯竞品基线

- 固定比较日期、仓库、默认分支、对应 README 和最多 1–3 个行为关键文件。
- 为每个对标对象填写第 3 节证据表，标记“已证实”、“推断”和“未验证”。
- 输出 `docs/competitive-analysis.md`，不用 Star 数或功能数代替实际工作流对比。
- 单独对比同类项目的能力发现、运行时选型、角色调度和自包含安装，为第 4 节闭环提供证据。

验收：每一条拟借鉴的机制都能回指到竞品的具体文档或代码证据。

### Phase B：修复三个 P0 契约缺口

- 把项目模板收入 `ai-creation-workflow` 内部的可安装资产，保留仓库顶层兼容入口，并用安装测试防止两份漂移。
- 把 `stale` 纳入状态契约、模板和恢复说明，增加“仅受影响节点失效”测试。
- 将退役证据拆成必填的结构化契约：替代者、替代测试、独特能力处置、同题 A/B、近期使用和项目依赖、许可证审查。`retire` 执行前再次验证契约和 Skill 指纹。

验收：单独安装总控后模板可用；状态集合只有一个权威定义；缺少任一退役证据时计划无法进入 `ready`。

### Phase B2：实现技能管家的能力补齐闭环

- 为 `skill-governor` 增加能力签名、适配判定、路由缓存和缺口状态契约。
- 复用现有注册表实现“短名单优先”，仅在必要时升级为本地全库检查。
- 增加可替换的在线搜索适配器，默认先用本地索引，不足时才查在线目录/GitHub；搜索与安装分开。
- 增加统一候选入口：用户指定候选跳过发现搜索，管家找到的候选保留搜索证据，两者都经过能力查重和安全/许可审查。
- 增加 `full_install | reference_strengthen | reject` 采纳决策；用户已指定方式时不再问，未指定时带推荐只问一次。完整安装与参考补强都先进 staging，并防止生成重复目录或无意覆盖已有能力。
- 增加候选审查、能力缺口规格和 `create | improve | use-tool` 决策；没有合格候选时，创建/改进始终先进 staging。
- 总控只保存返回的决策摘要和产物路径，不携带搜索全文进入后续阶段。

验收：已有合格 Skill 时不访问网络；本地缺口时才搜索在线；用户给定候选不重复搜索但仍查重审查；未指定采纳方式时只问一次，已指定时不重复问；参考补强不创建重复目录；完整安装先进入 staging/probation；无候选时生成最小创建/改进方案；签名不变的续作不重复搜索。

### Phase C：吸收竞品优点，保持双核心边界

- 参考视频专项项目，给 AI 视频领域包增加“单镜头快速路径 / 成套项目路径”和“高风险样片先行”决策，不改总控核心。
- 参考 LangGraph，完善状态转移表、恢复起点和外部任务幂等性测试；继续使用 JSON/文件状态，不增加服务端依赖。
- 参考 CrewAI，在计划中记录“为什么委派 / 为什么不委派”、输入包指纹、写入范围和验收证据；不把子代理当默认。
- 参考 Agent Skills 自包含结构，添加“安装到临时空目录后再验证”的发布门禁。

验收：每项改动都有对应故障场景测试，并能说明为什么没有引入竞品的重依赖或额外门禁。

### Phase D：双核心行为前向验收

使用固定请求集合验收，不只检查关键字：

1. 模糊的非视频多阶段任务：总控先定位一个关键缺口，不加载 H3。
2. 完整的单步请求：走 direct，不建立大型项目文件。
3. 两个互不依赖的 `ready` 节点：仅在写入不冲突、输入/验收完整且有实际收益时委派。
4. 两个共用一文件的节点：必须串行。
5. 上游决策更改：只把依赖旧版输入的下游标记为 `stale`。
6. H3 未指定运行位置：只问云端还是本地；指定后不重复问。
7. 云端超时：只恢复已记录的 `prompt_id`，不重复提交付费任务。
8. 退役 Skill：缺一项证据就失败；完整后可归档并恢复。
9. 更新 Skill：本地改动不被盲目覆盖，冲突停在 staging。
10. 单独安装两个核心 Skill：所有直接引用、脚本和模板均可用。
11. 已有完全胜任 Skill：直接复用路由，不全库扫描、不访问网络。
12. 已有 Skill 部分胜任：只搜索和测试缺失部分，不替换无关能力。
13. 本地无候选、在线有合格项：输出来源/许可证/风险/回滚完整的单次批准卡，不自动安装。
14. 本地与在线都无合格项：生成窄范围能力规格，正确选择局部优化、新建 Skill 或直接用工具。
15. 同一节点说“继续”：读取现有 `routing-decision` 和 `gap-resolution`，不重复搜索和深读候选。
16. 用户给出第三方 Skill 但没说采纳方式：跳过在线发现，完成查重/增益/安全/许可审查，带推荐只询问一次完整安装还是参考补强。
17. 用户已明确完整安装：不重复提问；候选进入 staging，通过测试后以 `probation` 激活，重复能力保持显式映射和较低初始优先级。
18. 用户选择参考补强：不新增 Skill 目录，只把许可允许且能改变决策的部分更新进现有 Skill，并保留归属、指纹和回归证据。
19. 候选与现有 Skill 实质重复且无可测增益：推荐不采用并缓存拒绝证据，后续不重复深审。

验收：独立结果审查不提供预设结论；回收实际输出、文件和测试证据。

### Phase E：发布前审计与 GitHub 更新

- 运行全部 Python/JSON/Skill 结构、内部链接、安装、生命周期、领域包、云/本地 dry-run 和 Windows/Linux CI 检查。
- 扫描 JWT、私有绝对路径、本机注册表、缓存和生成资产。
- 同步中英文 README，更新竞品对标结论和“采用/不采用”决策。
- 先 `fetch` 确认远端无新提交，再提交、推送 `main`，最后回读 GitHub 的提交 SHA 和 CI 状态。

验收：工作树干净，本地与 `origin/main` 指向同一提交，GitHub CI 全部通过；失败时不标记发布完成。

## 7. 迭代优先级

| 优先级 | 内容 | 原因 |
|---|---|---|
| P0 | 自包含安装、`stale` 契约、结构化退役证据 | 当前文档承诺与真实行为不一致 |
| P0 | Skill 胜任判定、本地/在线补齐、统一候选查重、完整安装/参考补强闸门、无候选自建/优化、路由缓存 | 是技能管家能否真正“管理和补齐能力”、又不让 Skill 重复膨胀的主闭环 |
| P1 | 状态转移/幂等恢复测试、委派决策记录、视频快速路径与样片策略 | 能提高真实可用性并降低 Token/重试成本 |
| P2 | 更完整的可观测报告、更多领域包 | 有价值，但不应延迟当前发布 |
